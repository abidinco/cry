# Görev 01 — WireGuard tünelini çalışır hale getir

## Rolün

Bu görevi sen yürüteceksin. Kullanıcıya adım adım komut verip "çıktıyı yapıştır"
deme — komutları kendin çalıştır, çıktıyı kendin oku, kararı kendin ver.
Kullanıcıya yalnızca senin erişemediğin şeyler için sor (aşağıda listeli).

## Amaç

`https://cry.abidin.dev` adresine gelen isteğin, Hetzner sunucusundan WireGuard
tüneli üzerinden evdeki Windows makinesinde çalışan uygulamaya ulaşması.

```
tarayıcı → cry.abidin.dev (65.21.108.193)
         → Caddy (proxy-caddy konteyneri, /srv/proxy/Caddyfile)
         → wg0 tüneli → 10.99.0.2:1337 (bu Windows makinesi)
```

## Ortam

**Sunucu (Hetzner):** Ubuntu, `65.21.108.193`, dış arayüz `eth0`. Root erişimi
`sudo -i` ile. Reverse proxy Docker içinde Caddy (`proxy-caddy` konteyneri,
Caddyfile `/srv/proxy/Caddyfile`, statik dosyalar `/srv/landing`). ufw pasif.
Üzerinde pt.abidin.dev, hessap.la, hafiza.abidin.dev, blog.abidin.dev çalışıyor —
**bunlara zarar verme.**

**PC:** Windows, WireGuard GUI kurulu.

## Parametreler

| | |
|---|---|
| Sunucu WG IP | `10.99.0.1` |
| PC WG IP | `10.99.0.2` |
| WG portu | `51830/UDP` |
| Uygulama portu | `1337` |
| WG ağı | `10.99.0.0/24` |

## Şu ana kadar yapılanlar

Sunucuda:
- `wireguard` kuruldu, anahtarlar `/etc/wireguard/server.key` ve `server.pub`
- `/etc/wireguard/wg0.conf` yazıldı, `wg-quick@wg0` çalışıyor
- Caddyfile'a `cry.abidin.dev` bloğu eklendi, çevrimdışı sayfası
  `/srv/landing/cry-offline.html` oluşturuldu, Caddy reload edildi

PC'de:
- WireGuard tüneli oluşturuldu (Address `10.99.0.2/24`, Endpoint
  `65.21.108.193:51830`, AllowedIPs `10.99.0.1/32`, PersistentKeepalive 25)
- Güvenlik duvarı kuralı `cry-app-wg` eklendi (TCP 1337, kaynak 10.99.0.0/24)

## Mevcut arıza

`wg show` çıktısında peer görünüyor ama **latest handshake satırı yok.**
Sunucudan `ping 10.99.0.2` "Destination Host Unreachable / sendmsg:
Destination address required" veriyor — bu, WireGuard'ın peer'ın gerçek
internet adresini hiç öğrenmediği anlamına gelir. Yani PC'den sunucuya tek bir
geçerli WireGuard paketi bile ulaşmamış.

Ayrıca test için çalıştırılan `python -m http.server 1337` yalnızca IPv6'da
dinliyordu (`Serving HTTP on ::`). Windows'ta IPv6 soketi IPv4 bağlantılarını
kabul etmez, yani tünel düzelse bile bu test başarısız olurdu. Testlerde
`--bind 0.0.0.0` kullan.

## Teşhis sırası

Sırayla ilerle, ilk eşleşen nedende dur ve düzelt.

### A. PC tarafında tünel gerçekten aktif mi

```powershell
Get-Service WireGuardTunnel$* | Format-Table Name, Status
Get-NetAdapter | Where-Object InterfaceDescription -like "*WireGuard*"
Get-NetIPAddress -AddressFamily IPv4 | Where-Object IPAddress -like "10.99.*"
```

`10.99.0.2` adresini taşıyan bir arayüz yoksa tünel aktif değil. Kullanıcıdan
WireGuard penceresinde **Activate** demesini iste (GUI'yi sen tıklayamazsın),
ya da yapılandırma dosyası mevcutsa servis olarak kur:

```powershell
& "C:\Program Files\WireGuard\wireguard.exe" /installtunnelservice "<conf yolu>"
```

### B. Paketler sunucuya ulaşıyor mu

Sunucuda 25 saniye dinle, bu sırada PC'de tüneli yeniden başlat:

```bash
timeout 25 tcpdump -ni eth0 udp port 51830
```

PC tarafında yeniden başlatma:

```powershell
Restart-Service "WireGuardTunnel$<tünel adı>"
```

- **Hiç paket yok** → sunucuya ulaşmıyor. Hetzner Cloud Firewall'a bak.
  Kullanıcının `hcloud` CLI'ı veya API token'ı varsa kendin kontrol et; yoksa
  kullanıcıdan Hetzner panelinde Firewalls bölümünü kontrol etmesini iste —
  tanımlı kural varsa 51830/UDP gelen trafiğe açılmalı. Kural yoksa ev
  tarafındaki bağlantı UDP'yi engelliyor olabilir (mobil/kurumsal bağlantılarda
  görülür); bu durumda C şıkkına geçmeden önce kullanıcıya bildir.
- **Paket var, handshake yok** → anahtar uyuşmazlığı. C'ye geç.

### C. Anahtar karşılaştırması

Sunucuda:

```bash
wg show wg0 peers          # sunucunun beklediği PC açık anahtarı
cat /etc/wireguard/server.pub
```

PC'de tünel yapılandırmasındaki `PublicKey` değeri ile `server.pub` birebir
aynı olmalı; PC'nin kendi açık anahtarı ile `wg show wg0 peers` çıktısı birebir
aynı olmalı. En sık hata: kopyalarken sondaki `=` karakterinin düşmesi.

Uyuşmazlık varsa sunucudaki peer'ı düzelt:

```bash
wg set wg0 peer <ESKI_PUB> remove
wg set wg0 peer <DOGRU_PUB> allowed-ips 10.99.0.2/32
wg-quick save wg0
```

**Gizli anahtarları (`server.key`, PC'nin PrivateKey'i) hiçbir çıktıda, logda
veya dosyada gösterme.**

### D. Uygulama katmanı

Tünel kurulduktan sonra:

```powershell
python -m http.server 1337 --bind 0.0.0.0
```

Sunucudan:

```bash
ping -c 3 10.99.0.2
curl -sI http://10.99.0.2:1337 | head -1
curl -sI https://cry.abidin.dev | head -1
```

Ping çalışıp curl takılıyorsa sorun Windows güvenlik duvarında ya da
uygulamanın yalnızca localhost'a bağlanmasında. Kuralı doğrula:

```powershell
Get-NetFirewallRule -DisplayName "cry-app-wg" | Get-NetFirewallAddressFilter
```

## Sunucuda dikkat

- `set -e` ile çalış, yarım iş bırakma.
- Caddyfile'ı değiştirmen gerekirse **önce yedekle**, sonra
  `caddy validate` ve `caddy reload` çalıştır. `grep -c "cry.abidin.dev"
  /srv/proxy/Caddyfile` sonucu **1** olmalı — 2 ise "ambiguous site definition"
  hatası alınır (bu daha önce yaşandı).
- Diğer dört siteyi bozacak hiçbir değişiklik yapma.

## Kullanıcıdan istenebilecekler

Sadece şunlar için sor, gerisini kendin hallet:
- WireGuard GUI'sinde Activate/Deactivate tıklaması
- Hetzner Cloud paneline giriş gerektiren kontroller
- Sunucuya SSH erişimi yoksa bağlantı bilgisi

## Bitti sayılma kriteri

Üçü birden sağlanmalı:

1. Sunucuda `wg show` çıktısında peer için güncel bir "latest handshake" var
2. Sunucudan `curl -sI http://10.99.0.2:1337` → `200 OK`
3. Sunucudan `curl -sI https://cry.abidin.dev` → `200 OK`

Ek olarak PC'de tünel açılışta otomatik bağlanıyor olmalı (servis olarak
kurulu). Bunu da doğrula.

Bittiğinde kısa bir özet yaz: sorun neydi, ne yapıldı, hangi durumda.
